# discover-testing Router Reference

> Generated by `scripts/generate_skill_composition_views.py`. This is a self-contained local reference for the Router Skill; it has no repository-outside file dependency and does not turn composition into an installation dependency.

## Boundaries

- Select the single route that best matches the user's goal.
- Return one primary Skill and at most one optional Skill; do not emit a menu of candidates.
- Preserve assumptions and evidence gaps when information is incomplete; this reference does not prove model, runtime, or business effectiveness.

## Routes

### New feature quality readiness (`new-feature-quality`)

- Intent: Turn a new requirement and acceptance goal into testable quality preparation
- Applicable phase: Requirements analysis / test design
- Primary Skill: `requirements-analysis`
- Optional Skill: `test-strategy`
- Handoff: Hand off confirmed risks, acceptance conditions, and test scope for test design
- Not for:
  - Does not replace execution by a concrete test type or tool
  - Does not invent acceptance criteria when inputs are missing

### API delivery (`api-delivery`)

- Intent: Choose a starting point for contract and behavior validation of a new or changed API
- Applicable phase: API design / implementation / verification
- Primary Skill: `api-testing`
- Optional Skill: `api-contract-testing`
- Handoff: Hand off the endpoint inventory, input/output constraints, error paths, and contract risks
- Not for:
  - Does not replace execution by a concrete API client or framework
  - Does not treat contract checks as complete business acceptance

### Change and regression (`change-regression`)

- Intent: Identify change impact and narrow the regression scope
- Applicable phase: Change analysis / regression planning
- Primary Skill: `change-impact-analysis`
- Optional Skill: `regression-test-selection`
- Handoff: Hand off affected components, risk priorities, regression candidates, and evidence gaps
- Not for:
  - Does not claim that regression tests have been executed
  - Does not provide precise impact conclusions without change evidence

### Performance decision (`performance-decision`)

- Intent: Turn performance goals and workload assumptions into an explainable validation and analysis path
- Applicable phase: Performance modeling / result analysis
- Primary Skill: `performance-workload-modeling`
- Optional Skill: `performance-result-analysis`
- Handoff: Hand off workload assumptions, metric definitions, environment prerequisites, and analysis questions
- Not for:
  - Does not replace execution by a load-testing tool or target environment
  - Does not treat a static workload model as runtime results

### AI feature validation (`ai-feature-validation`)

- Intent: Separate functional behavior, model output, and risk-boundary validation for an AI feature
- Applicable phase: AI feature design / evaluation planning
- Primary Skill: `ai-feature-testing`
- Optional Skill: `llm-testing`
- Handoff: Hand off feature goals, input/output samples, risk dimensions, evaluation data, and unrun items
- Not for:
  - Does not claim model effectiveness without a model, data, and target environment
  - Does not treat prompt suggestions as business acceptance or security conclusions

### PR quality review (`pr-quality-review`)

- Intent: Review a Pull Request diff, test impact, test effectiveness, and quality evidence
- Applicable phase: Code review / test impact / quality gate
- Primary Skill: `pr-quality-review`
- Optional Skill: none
- Handoff: Hand off PR ID, base/head SHA, diff, acceptance criteria, available test evidence, and permission scope
- Not for:
  - Do not select the full workflow for a single code-review task
  - Does not post comments or approve merges on behalf of an authorized user

### Requirement to test design (`requirement-to-test`)

- Intent: The user explicitly requests requirement analysis through strategy, test cases, and traceability
- Applicable phase: Requirement quality / testability / test design
- Primary Skill: `requirement-to-test`
- Optional Skill: none
- Handoff: Hand off requirement IDs/text, acceptance criteria, business constraints, confirmed risks, and execution limits
- Not for:
  - Use a single requirement-analysis Skill for one clarification task
  - Does not invent unconfirmed business rules

### Change to regression plan (`change-to-regression`)

- Intent: The user explicitly requests change impact, regression selection, and risk synthesis
- Applicable phase: Change impact / regression planning
- Primary Skill: `change-to-regression`
- Optional Skill: none
- Handoff: Hand off diff, base/head SHA, modules/business paths, test inventory, time and environment limits
- Not for:
  - Use single-step impact analysis when only affected modules are requested
  - Does not claim regression has run

### Bugfix verification (`bugfix-verification`)

- Intent: Starting from a defect, reproduction steps, baseline, and fix version, establish reproduction, fix verification, and regression evidence
- Applicable phase: Defect reproduction / fix verification / regression
- Primary Skill: `root-cause-analysis`
- Optional Skill: `regression-test-selection`
- Handoff: Hand off the defect ID, reproduction input, baseline and target SHAs, fix diff, regression candidates, execution state, and evidence paths
- Not for:
  - Does not claim reproduction without baseline evidence
  - Does not treat a passing test alone as proof that the defect is fixed or as release approval

### AI evaluation gate (`ai-eval-gate`)

- Intent: Define evaluation gates, sample sizes, and release evidence for AI feature, Prompt, or model changes
- Applicable phase: Evaluation design / release gate
- Primary Skill: `quality-gate-design`
- Optional Skill: `llm-evaluation-design`
- Handoff: Hand off the evaluation goal, dataset and version, judge, thresholds, sample size, regression baseline, and unrun items
- Not for:
  - Does not design dataset and judge details; hand those to llm-evaluation-design
  - Does not replace release approval

### AI-generated code verification (`ai-code-verification`)

- Intent: Review production code written or changed by an Agent for intent, scope, dependencies, tests, and CI evidence
- Applicable phase: Implementation review / change verification
- Primary Skill: `ai-generated-code-review`
- Optional Skill: none
- Handoff: Hand off intent/acceptance criteria, base/head SHAs, generation provenance, complete diff, dependencies, raw test/CI results, and unverified items
- Not for:
  - Does not replace the full PR quality workflow
  - Does not infer implementation correctness or code verification from passing tests alone

### AI feature release lifecycle (`ai-feature-release`)

- Intent: Connect AI evaluation assets and gates to canary/shadow rollout, online quality monitoring, and rollback readiness
- Applicable phase: Evaluation / release gate / online monitoring
- Primary Skill: `ai-feature-release-workflow`
- Optional Skill: none
- Handoff: Hand off model/prompt/dataset/judge/run versions, gates and samples, rollout cohort, monitoring Owner, stop/rollback conditions, and pending decisions
- Not for:
  - Does not replace an evaluation engine, CI runner, or production monitoring system
  - Does not execute releases, traffic changes, risk acceptance, or human approval

## Handoff after selection

State the routing reason, key assumptions, evidence gaps, and next handoff input; composition is navigation, not a mandatory execution chain.
