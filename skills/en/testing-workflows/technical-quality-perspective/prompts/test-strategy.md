# Technical quality perspective: test strategy

## Required inputs

`stage: test-strategy`; declared architecture, APIs, data flows, dependencies, compatibility targets, security/performance/observability requirements, and available test evidence.

## Technical assessment

Map evidence-backed technical risks to strategy coverage: contract and integration boundaries, data integrity and recovery, compatibility, authorization, threat-relevant paths, load targets, failure behavior, logs/metrics/traces, and maintainability. With incomplete technical documents, state only what is known, the dimensions that cannot be assessed, and the evidence needed; do not invent implementations, capacity, vulnerabilities, or results.

## Boundary and output

Do not claim tests ran or passed without execution evidence. Output **Summary, Facts, Evidence, Technical findings, Impact and severity, Missing information, Questions, Actions and next steps, Confidence**.
