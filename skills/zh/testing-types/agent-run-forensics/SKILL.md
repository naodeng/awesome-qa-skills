# Agent 运行取证（中文版）

## 何时使用

- 需要解释一次已经发生的 Agent 运行：哪一步改了文件、为什么执行了某条命令、构建在哪里断的。
- 需要复现同事报告的失败，但没有对方的 API key、机器或当时的上下文。
- 需要把一次翻车的会话固化成回归用例，用录像而不是报告人的机器重新跑。
- 需要审计一次运行真正触碰过的文件与命令，包括没人提起过的那些。
- 有人拿「Agent 自己的解释」当结论，而你需要判断这个结论是否有证据支撑。

## 输出格式选项

- 默认输出 Markdown，便于评审和追加证据。
- 用户要求表格、CSV、JSON 或工单格式时，必须保留「结论 / 证据来源 / 是录到的还是推断的 / 置信度」这四个字段。
- 输出进入自动化流程时，先确认 `recorded` 与 `inferred` 两种边的枚举值如何表达，不要合并成一列。

## 如何使用

1. 每次执行必须先读取并遵循 `prompts/agent-run-forensics.md`，它是本 Skill 的完整执行规范。
2. 先确认读取工具与录像都在；缺哪个就明说哪个，然后停下，不要改用「回忆 + 推理」补齐。
3. 「为什么」类问题走因果链定位到单个事件，不要通读整条时间线再猜。
4. 每条结论标明来自 `recorded`（录到的）还是 `inferred`（查询时按规则推出来的），后者必须写出所依据的规则。
5. 需要复现时，先读录像里记录的 shell 命令，列出重放会真实重复执行的副作用，并逐项取得批准。

## 工具与依赖

本 Skill 读取的是 **OrcaReplay**（Apache-2.0，`Continuum-AI-Corp/OrcaReplay`）产生的录像。它是外部依赖，**只复制这个目录拿到的是方法，不是读取工具**。

- **只检查，不安装。** 执行 `orca --version`。命令不存在时，说清缺的是什么、为什么需要它，然后停在这里。全局安装一个包、注册一个 MCP server，都是需要用户授权的副作用，本 Skill 不得自行执行。
- **告诉用户装什么。** `npm i -g orcareplay@0.5.0` —— 一个叫 `orcareplay` 的包，装出一个叫 `orca` 的命令，需要 Node 20+。**必须锁版本**：用另一个版本去读某个版本录下来的东西，是一种不会报错的偏差来源，而本 Skill 的全部前提就是忠实读取。
- **MCP 是可选的。** `orca mcp` 把录像库通过 stdio 暴露出来。是否注册由用户决定，客户端配置是 `{"mcpServers": {"orca": {"command": "orca", "args": ["mcp"]}}}`。下面每一步都能用 CLI 完成，MCP 只是便利，不是前置条件。
- **录像在哪、是什么。** 录像是本地文件，权限 `0600`，存放在 `orca list` 能列出的录像库里。磁盘格式是 Orca trace 规范（该仓库的 `spec/orca-trace-v0.md`，CC BY 4.0）；本 Skill 只读，不写。
- **命令入口。** `orca list`（到底有没有录像）、`orca show <run>`（时间线）、`orca graph --to <seq>`（到某一个事件的因果链）、`orca replay <run>`（复现）、`orca checkpoints <run>` 配合 `orca compare`（模型对比）、`orca record <agent>`（没有录像时去录一次）。
- **依赖不可用时怎么办。** 用一句话说明，指出缺的是什么，**关于那次运行的任何问题都不要凭回忆回答**。读不到证据属于「证据缺失」，不是「可以重建」。

## 核心约束

- **问的是「已经发生的事」，就必须先读证据再回答。** 录像存在时靠回忆作答是错的流程，哪怕这次蒙对了。
- **`recorded` 与 `inferred` 不能压进同一句话。** 「第 14 步删掉了它」和「从时间上看像是第 14 步——这条边是推断的」是两种不同强度的断言。
- **重放成功不等于确定性结论。** 模型没有被重新提问，是把录下的回复喂回去；「重新跑一次会不会还失败」是另一个问题。
- **模型侧出网被挡 ≠ 网络隔离。** 重放时 Agent 进程会再跑一遍，录下来的工具调用会真实再执行一次，自己开连接的工具照样触达网络。
- **重放默认全部拒绝。** 起点是：被重放的进程**网络不可达、环境里没有凭据、除临时副本外不挂载任何宿主路径、不暴露容器或编排器 socket**。录像里的命令需要哪一项，就单独解除哪一项，逐项向用户说明并取得批准。**通用容器不能替代这四条**：默认 bridge 网络、继承调用者环境、bind-mount 工作区或挂着 `/var/run/docker.sock` 的容器，把这条规则要防的风险一个不少地放了回来。
- **重放在临时副本里做。** 否则录像里的文件树会覆盖当前工作区，未提交的改动在重放期间不可见，重放被中断则可能持续不可见。如果项目在临时副本里起不来，就说明情况并停下，**不要退回到原地重放**。
- 不编造录像里没有的事件、文件、退出码或因果关系。

## 交付前自检

- [ ] 回答「已发生的事」之前，已确认读取工具装好、录像存在，并实际读取过。
- [ ] 「为什么」类问题用的是因果链定位，不是通读时间线后的推测。
- [ ] 每条因果结论都标了 `recorded` 或 `inferred`，推断的写清了依据规则。
- [ ] 首次重放前已读过录像里的 shell 命令，并列出会真实重复执行的副作用。
- [ ] 网络、凭据、宿主路径、容器 socket 四项是逐项批准的，不是一句「可以」全放开。
- [ ] 重放在临时副本中执行，工作区未提交的改动未受影响。
- [ ] 逐字引用了重放结论行，而不是用一句话概括它。
- [ ] 没有把「重放一致」说成确定性证明，也没有把「出网被挡」说成沙箱。

## 常见误区

- 录像存在却凭印象回答「为什么」，答案通顺、自信、偶尔是错的——这比「不知道」更糟。
- 把推断出来的因果边说成录到的。
- 把 `reused=3/5` 当成部分失败。Harness 会为自己发请求（额度探测、会话命名），重放不会重复这些。
- 把空录像当成「什么都没发生」，实际是没捕获到——通常是该 Agent 把服务地址写死、不读环境变量。
- 直接在工作目录重放，覆盖了正在修改的文件。
- 把「放容器里跑」当成重放安全的全部答案，却不说那个容器能触达什么。

## 最佳实践

- 先定位到那一个事件，再往外扩展，而不是反过来。
- 把「录像里有什么」和「我据此推出什么」在版面上分开写，读者能一眼看出哪些可以直接引用。
- 复现失败时，优先把录像本身作为交付物交给对方，而不是描述现象。
- 对比不同模型时，用仓库自己声明的验证命令，用退出码作为判据，不要用现场临时安装的工具。
