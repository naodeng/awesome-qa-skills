# 质量门禁设计 Prompt

围绕发布或交付入口的准入条件、证据要求、责任人与例外路径建立可执行、可评审、可追踪的证据边界和判断结果。

## 输入

先做输入审计，逐项记录 known、missing、conflicting、stale、out_of_scope、assumptions：

- known：来源直接支持的范围、质量门禁材料、约束或结果。
- missing：影响发布或交付入口的准入条件、证据要求、责任人与例外路径判断但尚未提供的材料。
- conflicting：来源之间不一致的目标、口径、条件或行为。
- stale：可能过期的架构、版本、指标、样本或记录。
- out_of_scope：不属于本 Skill、未授权或需要真实环境的动作。
- assumptions：为了形成受限初版而暂时采用的假设，必须写验证方法。

## 你要做的事

1. 用一句话复述目标、对象、范围和成功标准。
2. 审计输入的完整性、可信度、时效性和可比性，重点检查门禁目标、准入条件、证据来源、责任角色、例外与回滚。
3. 围绕质量门禁建立风险或失败模型，明确触发条件、预期关注点、影响和证据需求。
4. 把分析转成具体场景、断言、验证步骤、决策门槛或改进实验。
5. 给出剩余风险、证据缺口和下一步，不把假设包装成事实。

## 执行规则

- 每个关键结论都要说明来源、证据状态和验证方法。
- 场景至少包含前置条件、动作或刺激、预期结果或判断标准、所需证据和停止条件。
- 使用 P0/P1/P2/P3 或等价分级，并解释业务影响、可能性、可探测性或决策成本。
- 具体覆盖发布或交付入口的准入条件、证据要求、责任人与例外路径，不以相邻测试类型、工具名或单个样例代替领域判断。
- 不编造数字、阈值、根因、系统行为、执行记录、全部通过或发布批准。
- 涉及生产、隐私或安全时默认使用最小权限、脱敏数据、mock、dry-run 或隔离环境。
- 将事实、推断、候选建议和 Human 决策分开；风险接受、例外和发布判断只能由 Human 确认。

## 领域操作与判定

以下步骤对提供材料进行设计或静态核对；fixture 判定、候选方案与真实执行证据分别记录。项目未提供的规则、门槛和授权保持待确认。

1. 为每个门槛记录义务、输入/版本/时效、比较符、PASS/FAIL、不可执行BLOCKED、缺证据或无法判断UNKNOWN的真值表；没有记录不得视为PASS。
2. 聚合规则由项目指定：必要门槛FAIL优先，无法验证按fail-closed停止；UNKNOWN/BLOCKED保持原因而不是折算失败率。所有必要门槛有新鲜有效PASS才可推荐通过。
3. 例外单列义务范围、授权人、理由、批准证据、有效期、补偿控制与撤销条件；过期/越界/无授权不生效，不改写原始FAIL。
4. 明确门禁触发、负责人、重新验证和回滚/停止条件；设计、静态证据判定与实际流水线实施分别报告，缺规则提交待Human决策。

## 评测证据状态与结构化追踪

当任务涉及评测、回归或结果审查时，为每个结论提供 `evaluation_status` 字段，枚举为 `PASS`、`FAIL`、`BLOCKED`、`NOT_RUN` 或 `UNKNOWN`。`PASS` 需要可追溯的实际运行记录和满足范围内全部必需断言的证据；没有运行结果时标记 `NOT_RUN`，尝试运行但被环境或权限阻止时标记 `BLOCKED`，证据不足以判断时标记 `UNKNOWN`。设计方案、静态检查或文件存在不能单独成为 `PASS` 证据。质量门禁或逐样本决定仍按其领域字段记录，与 `evaluation_status` 分开。

结构化追踪至少记录 `trace_id`、输入/样本 ID、模型/提示词/数据集/Schema 版本、影响结果的参数、run/trial ID、解析状态、Schema 状态、语义状态和证据引用。先独立检查 JSON 可解析性、Schema 约束和领域语义；解析成功不代表 Schema 或语义通过。脱敏原始输出或可复核哈希，保留重复次数和分母，不能用缺失证据填成通过。

## AI 评测门禁模式

AI 评测门禁除通用准入字段外，逐项绑定 `dataset_id/version`、模型/Prompt/judge 版本、`run_id`、数据来源和证据引用，并根据项目契约声明最低样本数/置信要求、质量阈值、flake 预算与成本预算。阈值必须有负责人和来源；不得由 Skill 自行设定业务门槛。

- 所有必需评测有新鲜、可追溯 run，样本数达到已批准门槛，且每项必要断言有证据，才可建议 PASS。
- 缺 run/版本/来源，样本量不足，judge 未校准，或结果为 `NOT_RUN`/`UNKNOWN` 时，门禁至少为 BLOCKED/UNKNOWN；不能把静态计划、部分样本或平均分转成绿灯。
- 分开报告质量失败、波动/flake、成本超限和线上护栏状态；例外需 Human 授权、范围、期限和补偿控制。

## 最低覆盖清单

- 门禁目标、准入条件、证据来源、责任角色、例外与回滚
- 已确认事实、当前假设、信息缺口、证据质量和时效性
- 高风险路径、阻塞条件、停止/升级/回滚或人工接管条件
- 最小验证动作、责任角色、关闭条件、剩余风险和 Human 决策
- 事实、证据支持的推断、候选建议、Human 决策

## 输出

### 1. 任务理解与范围

写明目标、对象、纳入项、排除项、成功标准和未授权动作。

### 2. 输入审计

分别列出 known、missing、conflicting、stale、out_of_scope、assumptions，并标明来源、时效性和证据质量。

### 3. 质量门禁分析与优先级

说明发布或交付入口的准入条件、证据要求、责任人与例外路径的场景、触发条件、预期行为、影响、优先级和证据缺口。

### QGD-## 发现合同

每条发现必须包含：

- 对象/规则
- 来源
- 触发条件或适用范围
- 预期关注点/理由
- 证据状态
- 影响/优先级
- 责任角色
- 关闭条件
- 验证方法

### 4. 候选验证与剩余风险

把候选建议和实际执行分开，写出最小验证动作、停止/升级条件、剩余风险和待确认问题。

### 5. Human 决策

只列需要 Human 确认、风险接受、例外授权、回滚或发布判断的事项。

输出必须同时保留以下分区：事实、证据支持的推断、候选建议、Human 决策。

## 质量要求

- 内容必须针对质量门禁，不能只是替换标题的通用模板。
- 高风险路径必须具体到失败模式、预期行为和证据。
- 数字、根因和系统行为不得无依据推断。
- 静态分析、计划或 dry-run 不等于真实执行、全部测试通过或发布已批准。
- 让执行者无需猜测下一步，让评审者能追溯事实、推断、建议和 Human 决策的边界。
