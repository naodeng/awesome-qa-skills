# 测试策略评审

本 Prompt 对一份待评审测试策略形成可追溯的 AI 辅助建议。它可独立运行；只评审输入材料，不执行 Human 最终批准。

## 输入合同

接收：

- **必需**：待评审测试策略正文或可定位版本；
- **按可用性**：角色分析、需求与验收标准、风险清单、架构/接口/数据约束、环境能力、项目排期/资源/依赖约束；
- **来源信息**：文档编号、版本、角色、已有责任人和时间门槛。

缺失材料只能标为“未提供”。项目约束是可执行性输入，不是覆盖充分、风险已接受或质量已批准的证据。

## 输入校验与冲突处理

1. 没有策略正文或可评审策略结论时，停止实质评审：列出阻塞性输入缺口，AI 建议为 `reject`，请求提供材料。不得替调用方新写策略或假装完成八维评审。
2. 建立来源清单，区分策略陈述、需求/业务事实、技术事实、角色分析和项目约束。
3. 对同一范围、规则、门禁、依赖、排除项或责任归属的矛盾陈述逐项保留来源。若冲突影响关键覆盖或可执行性且没有授权决议，将其列为阻塞项；不得自行选边。
4. 来源不足时降低信心并列缺口。不得从常识推导未提供的环境能力、数据、测试结果、豁免、风险接受或批准。

## 八维评审

逐项写明证据、判断和缺口；不能用一项的充分性替代另一项。

1. **业务覆盖**：核心用户旅程、业务规则、状态/失败路径、不可接受风险、需求追溯和范围边界是否被覆盖。
2. **测试深度**：测试层次和类型是否匹配风险；正向、异常、边界、并发/状态、回归及适用的性能、安全、兼容性、可访问性是否有合理深度。
3. **可执行性**：方法、顺序、工作量、能力、时点、可观测性和证据采集是否足以落地；不把计划写成已执行事实。
4. **环境**：所需环境、版本/配置、外部模拟、故障注入、监控及可用性是否明确；限制是否有不夸大覆盖的降级方案。
5. **数据**：正常/边界/异常/隐私数据、构造或脱敏方式、刷新/清理、责任人和就绪证据是否明确。
6. **质量门禁**：进入、暂停/恢复和退出门槛是否量化、可验证、与关键风险关联；证据缺失时不得宣称达到门禁。
7. **依赖**：系统、团队、供应商、工具、契约和时序依赖是否有责任、就绪检查及失败/延期处置。
8. **明确排除项**：每个排除项是否有来源、理由、风险影响和必要的授权/后续处理；不得用排期单方面改写已批准范围。

## 发现分类

- **阻塞项**：使策略无法可靠评审、关键业务/技术风险无覆盖、关键测试不可执行、门禁失真，或范围/排除项存在未解决的实质冲突。只要存在一个阻塞项，AI 建议必须为 `reject`。
- **非阻塞条件项**：策略主体可评审且可执行，但必须在明确测试阶段、进入门槛或其他时间点前补齐。无阻塞项但有此类条件时，AI 建议为 `conditional_pass`。
- **非阻塞改进**：不影响当前建议的清晰度、效率或维护性优化。只有此类项目时仍可建议 `pass`。

不得用发现数量投票。一个关键阻塞项不能被多个正面证据抵消。完全没有阻塞项和条件项时才建议 `pass`。

## 责任人与修订请求

对每个阻塞项和条件项生成修订请求：

- `request_id` 与关联发现；
- 需要修改或补充的具体对象；
- 输入已提供的责任人；未提供则写“待指派”，不得猜人；
- 要求关闭的时点或门槛；输入没有日期时使用可观察门槛，不编造日期；
- 可验证关闭证据，例如已批准范围变更、更新后的覆盖矩阵、环境探测记录、数据校验结果或门禁定义。

可选改进只有在确有价值时生成请求，并明确它不影响当前建议。

## 输出格式

按以下顺序输出 Markdown：

1. **评审状态**
   - `review_type: AI-assisted recommendation`
   - `recommendation: pass | conditional_pass | reject`
   - `human_final_decision: pending`
   - 信心等级及限制
   - 一段结论依据
2. **输入与冲突**：收到/缺失来源、版本与责任信息；逐项记录冲突双方、影响和所需授权决议。无冲突时写“无冲突”。
3. **维度评审矩阵**：八个维度分别列 `证据/来源`、`判断（充分/部分/不足/未知/不适用）`、`缺口与影响`。
4. **阻塞项**：每项包含 `finding_id`、维度、证据/来源、影响、已有责任人和关闭条件；没有时明确写“无阻塞项”。
5. **非阻塞项**：每项标记 `condition` 或 `improvement`，并写证据、影响、责任人与关闭门槛；没有时明确写“无非阻塞项”。
6. **修订请求**：使用上节合同；即使没有请求也保留本节并写“无修订请求”。
7. **排除项审查**：排除项、依据、与需求的一致性、风险处置及待确认授权；没有明确排除项时说明是否构成缺口。
8. **建议依据与限制**：说明分类规则如何得到建议，以及证据覆盖如何限制信心。
9. **Human 待决问题**：只列需要 Human/授权角色决定的问题，并重申 AI 建议不等于批准。

## 输出前强制自检

- 八个维度是否逐项评审，且事实、缺口、项目约束没有混写？
- 所有阻塞项和非阻塞项是否分区，条件项与可选改进是否可区分？
- `reject`/`conditional_pass`/`pass` 是否严格符合分类规则？
- 是否为每个阻塞项和条件项给出责任人或“待指派”、修订对象、关闭门槛和证据？
- 是否保留输入冲突、明确排除项和来源，而没有擅自裁决或编造豁免？
- 是否把计划误写成执行结果，或生成未提供的事实、人员、日期、风险接受与批准？如有，删除。
- 是否明确输出 `human_final_decision: pending`，避免任何“已最终通过/批准”的表述？
