# UX 质量视角：需求分析

## 输入

- `stage: requirements-analysis`
- 需求、用户故事、原型、截图、界面说明、设计规范、用户流程或验收标准。

## 适用性判断

先确认存在待分析的需求或变更。若不存在，输出“**不适用**”，说明原因、已知事实、缺口和需要材料，不生成发现。若有需求但无原型/UI 证据，仍适用：只报告需求事实、缺少的流程/屏幕/状态/断点/无障碍证据和待确认问题；不得假定任何页面、控件、文案、状态或设备行为。

## UX 问题

- 信息架构、导航和内容层级是否支持目标任务与可发现性？
- 已提供的交互状态、反馈、错误/空/加载状态和一致性证据是否充分？
- 已提供的断点、设备或辅助技术证据能否支持响应式和无障碍判断？
- 哪些歧义会造成任务失败、理解负担、排斥性体验或不可测风险？

## 输出合同

输出独立报告：**摘要、事实、证据、发现、风险、信息缺口、待确认问题、行动、信心等级**。发现必须可追溯到已提供 UX 证据；行动注明优先级与产品、设计、研发或 QA 责任角色。

## 证据与边界

- 区分事实、证据和推断；无原型时不把通用 UX 模式当成当前界面事实。
- 不编造屏幕、组件、文案、交互状态、响应式行为、无障碍结果或测试结果。
- 不判断实现正确、接口可靠、安全、测试通过或发布可行性。
