# 需求到测试工作流

提供需求、用户故事或验收标准后调用 `requirement-to-test`，获得测试策略、用例和追踪矩阵。

## 示例

> 分析 R-17“账户冻结时不得退款”。先检查可测试性，列待确认规则，再给正向/负向用例、风险策略和 R-17 追踪关系。

## 最佳实践

保留需求 ID；阈值缺失时提问；标出每个用例的来源和方法；说明未覆盖原因。

## FAQ

- 验收条件模糊时只问影响范围、判定和优先级的问题。
- 默认不运行测试；执行状态为 `NOT_RUN`，真实运行证据单独引用。
- 需求指纹或规格版本改变后，旧 Checkpoint 标 `STALE` 并重审。
