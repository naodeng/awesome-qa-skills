# 测试生命周期 Skill 图集设计

## 目标

基于仓库当前中文 Skill 目录与工作流定义，制作三张相互补充的 Archify 交互图，帮助读者理解：

1. 完整测试生命周期各阶段应使用哪些主 Skill。
2. 请求如何经路由、工作流门禁、类型 Skill 和角色汇总形成可交付产物。
3. 日常、迭代、发布三类工作流如何复用相同的类型 Skill。

图集只表达仓库已经存在的能力与约束，不虚构运行时编排、自动调用或测试执行结果。

## 受众与使用场景

- 初次使用仓库、需要按测试阶段选择 Skill 的 QA、开发和项目成员。
- 需要解释仓库 Skill 分层、工作流边界和阶段交接方式的维护者。
- 需要在项目文档、培训或评审中展示测试生命周期的读者。

## 交付物

在 `docs/diagrams/testing-lifecycle-skills/` 下保存三组 Archify JSON 源文件与独立 HTML：

| 图 | 类型 | JSON / HTML 基名 | 核心问题 |
| --- | --- | --- | --- |
| 完整测试生命周期全景图 | `workflow` | `testing-lifecycle-overview` | 每个测试阶段使用什么 Skill？ |
| 阶段与 Skill 路由图 | `dataflow` | `stage-skill-routing` | 请求和产物如何在各层之间流转？ |
| 日常—迭代—发布三级协作图 | `workflow` | `workflow-levels-collaboration` | 三种节奏如何复用类型 Skill 与门禁？ |

每张 HTML 为自包含交互图，采用静态默认视图，不启用动画。读者文案使用中文；Skill 名、命令和代码标识保留英文。

## 图 1：完整测试生命周期全景图

### 主路径

需求分析 → 测试策略 → 策略评审 → 代码审查 → 用例编写 → 用例评审 → 测试执行 → 缺陷闭环 → 测试报告 → 报告评审 → 发布决策。

### Skill 映射

- 需求分析：`requirements-analysis`
- 测试策略：`test-strategy`
- 策略评审：`test-strategy-review`
- 代码审查：`code-review`
- 用例编写：`test-case-writing`
- 用例评审：`test-case-reviewer`
- 测试执行：以 `functional-testing` 为主路径代表，专项测试作为侧分支
- 缺陷闭环：`bug-reporting`
- 测试报告：`test-reporting`
- 报告评审：`test-report-review`
- 发布决策：由 `release-testing-workflow` 管理门禁，Human 保留最终决定权

专项执行分支按视觉容量分组展示：接口与 UI、移动与可访问性、性能与安全、自动化。图中使用仓库真实 Skill 名，不把工具专项 Skill 全部铺开，避免全景图退化为目录清单。

### 视觉重点

- 一条清晰的左到右主路径。
- 评审节点与 Human 决策使用明显的门禁语义。
- 测试执行的专项分支保持短小，并回收到执行证据与报告主线。

## 图 2：阶段与 Skill 路由图

### 数据流

用户测试请求进入 `discover-testing`，识别主要目标和阶段；随后选择一个主要工作流或类型 Skill。日常、迭代、发布工作流负责节奏、门禁与下一跳，类型 Skill 负责具体分析或测试产物。

当同一阶段存在多个角色报告时，由 `multi-role-quality-synthesis` 合并等价发现、保留来源与分歧，再把阶段汇总交给评审 Skill 或下一阶段。最终产物包括策略、用例、执行/缺陷证据、测试报告和评审建议。

### 关键约束

- 路由默认选择 1 个主 Skill，仅在必要时补充 1 个辅助 Skill。
- 工作流 Skill 管阶段和门禁，不代写类型 Skill 的完整产物。
- 类型 Skill 独立安装、自洽，不依赖其他 Skill 的私有文件。
- 多角色汇总只合并调用方提供的同阶段报告，不新增事实。
- 策略评审、报告评审和发布决策均保留 Human 最终决定权。

### 视觉重点

- 以数据流而非目录树表达“请求 → 路由 → 编排/执行 → 汇总/评审 → 产物”。
- 工作流层、类型 Skill 层、汇总与门禁层使用明确分组。
- 只保留能说明职责边界的连接，避免形成多对多线团。

## 图 3：日常—迭代—发布三级协作图

### 三条节奏

- 日常：晨间计划 → 测试执行 → 缺陷跟进 → 日终收口。
- 迭代：规划 → 设置 → 执行 → 回归 → 稳定 → 评审。
- 发布：T-N 规划 → 专项验证 → RC → Go/No-Go → 发布后观察。

### 共享能力

三类工作流通过阶段交接复用同一组类型 Skill：需求与策略、用例设计、专项执行、缺陷报告、测试报告。工作流本身只管理节奏、范围、门禁、退出证据与下一跳。

### 视觉重点

- 三条泳道分别表达日常、迭代和发布节奏。
- 共享类型 Skill 作为共同能力带，避免为每条泳道复制一套节点。
- 日常证据汇入迭代门禁，迭代证据汇入发布门禁；不得暗示时间流转本身等同于测试通过。

## 内容边界

本次不包含：

- 角色 × 阶段的全部 Prompt 文件展开。
- 36 个测试类型 Skill 的完整目录清单。
- 工具专项 Skill 的安装方式或命令。
- 动画、演示章节、深链接或自定义 Viewer Runtime 功能。
- 对 README、索引或 Skill 内容本身的修改。

## 验证与验收

每张图必须满足：

1. JSON 设置 `meta.quality_profile` 为 `showcase`。
2. `archify validate` 报告 9 项 artifact checks、0 composition errors、0 warnings。
3. `archify deliver` 成功并返回规格与 HTML 的 SHA-256 和字节数。
4. `archify visual-check` 检查 1440×900、1600×1000、1920×1080、2048×1320；所有尺寸无水平或垂直溢出。
5. 人工检查最小与最大尺寸的明暗主题截图或 contact sheet，确认主路径清晰、中文可读、无明显空白失衡、遮挡或歧义连线。
6. 最终运行 `git diff --check`，并扫描设计、JSON 与交付说明中的 `TBD`、`TODO` 和未替换占位符。

若某张图连续两轮定向修复都无法降低 Archify 的客观错误数，则停止扩张改动，如实记录未解决诊断，不把失败描述为成功。
